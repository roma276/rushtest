# Raft AI4BI — тестовое задание

Репозиторий содержит артефакты выполнения тестового задания на роль **технического руководителя проектов внедрения AI4BI** для ООО «Севертрейд». Работа проходит путь от обследования и согласования ожиданий до модели данных, SQL, интеграций, постановки задачи разработчику, письма заказчику и гипотез развития аккаунта.

## Контекст проекта

По легенде задания, клиент — ООО «Севертрейд», дистрибьютор промышленного оборудования и расходных материалов. Первый домен — закупки, срок первого релиза — четыре недели. На стартовой встрече отмечены ежемесячный Excel-отчёт из 40 вкладок, который собирается три дня, расхождение закупочного и финансового оборота на 8–10%, разные значения OTIF (94% и 71%), потребность видеть ценовые различия и желание получать предупреждения о возможных срывах поставок.

Это факты из задания и встречи, а не результаты независимого аудита. Годовой оборот в легенде обозначен как `[X]` и не считается известным.

## Рекомендуемый порядок чтения

1. `block_1_discovery/01_discovery.md` — что узнали на встрече, что уточнить у клиента, границы релиза и риски.
2. `block_2_model/02_README.md` — навигация по материалам модели.
3. `block_2_model/02_model.md` — целевая модель данных и обоснование решений.
4. Остальные файлы `block_2_model/` — DDL, ER-диаграмма, метрики, трансформации, контроль качества и валидация.
5. `block_3_sql/README.md` — как устроены SQL-артефакты; далее запросы, CSV и скриншоты результатов.
6. `block_4_integration/04_integration.md` — описание интеграций; затем соответствующие диаграммы в `diagrams/`.
7. `block_5_task/05_task.md` — пример задачи, подготовленной для передачи разработчику.
8. `block_6_communication/06_client_email.md` — письмо заказчику по итогам встречи.
9. `block_7_account/07_account.md` — гипотезы расширения работ после первого релиза.
10. `AI_LOG.md` — прозрачность использования AI и проверка его выводов.

## Допущения и границы достоверности

- Описание бизнес-проблем основано на легенде и конспекте встречи.
- Значения OTIF 94% и 71% — конфликтующие цифры из встречи; без проверки методик нельзя утверждать, что одна из них правильная.
- Расхождение оборота 8–10% озвучено заказчиком, но его причины требуют сверки.
- Проектные решения в документе интеграций не обязательно являются уже реализованными свойствами систем клиента.
- Наличие исторических данных о заказах и приёмках само по себе не доказывает пригодность данных для прогнозирования срывов.
- Ценовой сигнал не равен подтверждённой экономии; его должен проверить закупщик.
- Оценки S/M/L в блоке 7 предварительные, не являются сметой или коммерческим обязательством.
- Нельзя считать SQL протестированным только потому, что в каталоге есть `.sql`, `.csv` или скриншот. Перед утверждением о проверке нужно подтвердить соответствие результата запросу и окружению.
