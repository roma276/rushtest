# [SRM] Реализовать отказоустойчивую загрузку тендеров и лотов

**Тип:** Backend / Integration  
**Приоритет:** High  
**Компонент:** SRM Integration  
**Связанные материалы:** `block_4_integration/04_integration.md`, диаграммы последовательностей SRM tenders/lots  
**Статус:** Ready for implementation после проверки допущений из раздела 10.

## 1. Контекст и цель

SRM API предоставляет тендеры через `GET /api/v2/tenders?page={n}&size={100}` и лоты через `GET /api/v2/tenders/{id}/lots`.

Ограничения API из исходного ТЗ:
- `updatedFrom` для тендеров отсутствует;
- сортировка по релевантности, порядок между вызовами не гарантирован;
- ориентировочный объём — 180 000 тендеров;
- лоты получаются по одному тендеру за запрос;
- лимит — 100 запросов в минуту на OAuth2-токен;
- OAuth2 `client_credentials`, TTL токена — 15 минут.

**Цель:** загрузка тендеров и лотов с сохранением прогресса, общим rate limit, ограниченными повторами и восстановлением после перезапуска без повторной обработки всех успешно завершённых заданий.

## 2. Границы

### Входит
1. Получение и обновление OAuth2-токена.
2. Общий rate limiter для всех SRM endpoint.
3. Постраничная загрузка тендеров.
4. Персистентный checkpoint после успешного сохранения каждой страницы.
5. Отдельные задания загрузки лотов для тендеров.
6. Ограниченные повторы временных ошибок.
7. Восстановление после перезапуска.
8. Идемпотентное сохранение по стабильным ID.
9. Логи, счётчики и итоговый статус.
10. Хранение неуспешных заданий для повторного запуска.

### Не входит
- Изменение SRM API или разработка batch endpoint.
- Гарантия обнаружения новых/изменённых тендеров после первичной загрузки.
- Автоматический повторный полный обход тендеров по расписанию.
- Разработка витрин и бизнес-метрик.
- Изменение формата WMS/Kafka.
- Обещание завершения первичной загрузки за одну ночь без замеров производительности.

## 3. Конфигурация

| Параметр | Значение по умолчанию | Примечание |
|---|---:|---|
| `page_size` | 100 | Не превышать лимит API |
| `rate_limit_per_minute` | 100 | Общий лимит на токен |
| `connect_timeout_seconds` | 5 | Предлагаемое, конфигурируемое |
| `read_timeout_seconds` | 30 | Предлагаемое, конфигурируемое |
| `max_retries` | 3 | Повторы сверх первой попытки |
| `backoff_base_seconds` | 1 | Начальная задержка |
| `backoff_max_seconds` | 60 | Кроме более длительного `Retry-After` |
| `token_refresh_margin_seconds` | 60 | Обновление до истечения |
| `max_parallel_lots_requests` | 1 | Консервативный старт, конфигурируемый |

Все численные значения, кроме ограничений исходного ТЗ, являются стартовыми настройками.

## 4. Алгоритм

### 4.1. OAuth2
1. Получить токен через `client_credentials`.
2. Прочитать `expires_in`, рассчитать время обновления с запасом.
3. Не писать токен и секреты в логи.
4. При HTTP 401 получить новый токен и ограниченно повторить исходный запрос.
5. При повторном 401 завершить конкретное задание с ошибкой авторизации; бесконечный цикл запрещён.

### 4.2. Загрузка тендеров
1. Прочитать состояние checkpoint; новое задание начинает с первой страницы.
2. Запросить `GET /api/v2/tenders?page=N&size=100` через общий rate limiter.
3. При успешном непустом ответе проверить структуру, сохранить записи идемпотентно по стабильному ID, зафиксировать транзакцию и только затем сохранить `N` как последнюю успешно обработанную страницу.
4. Увеличить номер страницы только после успешного commit.
5. Успешный ответ с пустым списком означает завершение обхода — это проектное допущение.
6. При таймауте, сетевой ошибке, 429 или 5xx использовать ограниченные повторы с backoff.
7. При ошибке checkpoint не продвигать.
8. После рестарта продолжить с сохранённого состояния, не начинать полный обход заново.

Ошибка HTTP, timeout, невалидный JSON или отсутствие тела не считается концом пагинации.

### 4.3. Задания лотов
Для каждого сохранённого тендера обеспечить одно задание с уникальным ключом `tender_id`.

Статусы:
- `PENDING` — ожидает обработки;
- `IN_PROGRESS` — выполняется;
- `SUCCESS` — данные сохранены;
- `FAILED` — попытки исчерпаны либо обнаружена постоянная ошибка.

### 4.4. Загрузка лотов
1. Выбрать `PENDING` или разрешённое к повтору задание.
2. Пройти общий rate limiter.
3. Выполнить `GET /api/v2/tenders/{tender_id}/lots`.
4. При успехе сохранить лоты идемпотентно по стабильному ID и поставить `SUCCESS`.
5. При временной ошибке увеличить счётчик и повторить с backoff.
6. После исчерпания попыток поставить `FAILED`, сохранить код/описание ошибки и продолжить обработку остальных тендеров.
7. Повторный запуск обрабатывает только неуспешные задания.

### 4.5. Обработка ошибок
- `401`: обновить токен и ограниченно повторить запрос.
- `429`: соблюдать `Retry-After`, если он присутствует; иначе backoff.
- `5xx`, сетевые ошибки, таймауты: ограниченные повторы.
- Остальные `4xx`: без автоматического повтора, кроме отдельно оговорённых случаев.
- Ошибка парсинга/контракта ответа не считается концом пагинации.
- Логировать endpoint, сущность/страницу, HTTP-код, длительность, номер попытки и ошибку; секреты не логировать.

## 5. Персистентное состояние

**Состояние обхода тендеров:** `job_id`, `status`, `last_successful_page`, `started_at`, `updated_at`, `completed_at`, `last_error`.

**Задания лотов:** `tender_id` (уникальный ключ), `status`, `attempt_count`, `next_attempt_at`, `last_http_status`, `last_error`, `created_at`, `updated_at`, `completed_at`.

Названия и типы можно адаптировать к соглашениям проекта. Нужны индексы по статусу и времени следующей попытки.

## 6. Критерии приёмки

1. Размер страницы тендеров не превышает 100.
2. Все запросы `contracts`, `tenders`, `lots` проходят через единый rate limiter.
3. На 429 нет цикла немедленных повторов.
4. На 401 обновляется токен и исходный запрос ограниченно повторяется.
5. Токен обновляется заранее по `expires_in`, если поле есть в OAuth-ответе.
6. Данные страницы фиксируются до продвижения checkpoint.
7. Пустой успешный ответ завершает обход; timeout/HTTP error/parse error — нет.
8. После рестарта обработка продолжается с последней сохранённой страницы.
9. Успешные задания лотов не запускаются повторно без необходимости.
10. Ошибка одного тендера не останавливает очередь остальных.
11. После исчерпания повторов задание `FAILED`, причина доступна.
12. Повторная обработка не создаёт дубли при наличии стабильных ID.
13. Итоговый статус содержит счётчики успешных/неуспешных заданий.
14. В логах отсутствуют токены и секреты.
15. Прогресс и статусы переживают аварийный перезапуск.

## 7. Тест-кейсы

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| TC-01 | Несколько непустых страниц, затем пустой список | Обход завершается; checkpoint — последняя непустая страница |
| TC-02 | HTTP 500 на странице | Ограниченные повторы; checkpoint не продвигается до успеха |
| TC-03 | HTTP 429 с `Retry-After` | Повтор не раньше указанной задержки |
| TC-04 | HTTP 429 без `Retry-After` | Используется backoff |
| TC-05 | 401 из-за токена | Новый токен, ограниченный повтор исходного запроса |
| TC-06 | Новый токен тоже получает 401 | Контролируемая ошибка, бесконечного цикла нет |
| TC-07 | Падение после commit страницы N | После рестарта продолжение со страницы N+1 |
| TC-08 | Падение до commit страницы N | Checkpoint не продвинут; страница N запрашивается повторно |
| TC-09 | Постоянная ошибка лотов у одного тендера | Его задание `FAILED`, остальные продолжаются |
| TC-10 | Повторная обработка страницы | Upsert не создаёт дубли |
| TC-11 | Невалидный JSON | Обход не считается завершённым |
| TC-12 | Повторное добавление `tender_id` в очередь | Нет дублирующего активного задания |
| TC-13 | Параллельные запросы разных endpoint | Общий лимит не превышается |
| TC-14 | Падение после 130 000-го тендера | Успешные задания сохранены; восстановление с checkpoint и незавершённых заданий |
| TC-15 | Запись без стабильного ID | Не сохраняется как полноценная сущность; ошибка регистрируется |

## 8. Наблюдаемость

Логи/метрики должны показывать текущую страницу и состояние обхода; количество полученных/сохранённых записей; число заданий лотов в каждом статусе; количество 401/429/5xx/timeout/retry; длительность запросов и задания; время последнего checkpoint; последнюю ошибку.

## 9. Definition of Done

- [ ] Реализованы HTTP-клиент, OAuth2 и общий rate limiter.
- [ ] Реализована постраничная загрузка и персистентный checkpoint.
- [ ] Реализована очередь лотов с указанными статусами.
- [ ] Реализованы идемпотентное сохранение и восстановление.
- [ ] Реализованы таймауты, повторы и backoff.
- [ ] Есть логи без секретов и необходимые метрики.
- [ ] Автоматизированные тесты покрывают позитивные и негативные сценарии.
- [ ] Проверено восстановление после имитации падения.
- [ ] Обновлена документация по конфигурации и ограничениям.
- [ ] Интеграционные тесты с реальным API выполнены только при наличии тестового доступа; отсутствие доступа явно указано.
- [ ] Ограничение полноты тендеров из-за нестабильной сортировки задокументировано.

## 10. Допущения и вопросы для проверки до production

1. Пустой список в ответе `/tenders` означает конец пагинации.
2. У тендеров и лотов есть стабильные ID для идемпотентного сохранения.
3. OAuth-ответ содержит `expires_in`; истёкший токен возвращает 401 с описанием ошибки.
4. `Retry-After` может отсутствовать.
5. Формат ответа и ошибок SRM проверяется на тестовом доступе.
6. Продолжение с номера страницы не гарантирует полноту данных из-за нестабильной сортировки. Повторный полный обход по расписанию не выполняется по согласованному решению.

Если допущение не выполняется, поведение согласуется и документируется до выпуска, а не определяется разработчиком самостоятельно.
