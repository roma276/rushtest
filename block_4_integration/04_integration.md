# Блок 4. Интеграции и пайплайны

Статус: проектное решение для разработки; допущения явно отмечены. Документ опирается на фрагмент SRM API и пример `wms.receipts.v1` из раздела 1.3 ТЗ, а также на согласованные в ходе проработки решения. Неподтверждённые особенности API/WMS не считаются фактами.

## 4.1. Целевой бизнес-процесс: от источников до витрин

### Источники и режимы

| Источник / процесс | Режим | Обработка и ограничения |
|---|---|---|
| 1С:УТ: шапки и строки заказов | Ночью, инкрементально | Использовать `updated_at` для строк, только если проверено, что он отражает все существенные изменения. Checkpoint двигать после успешного сохранения. Семантика изменений/удалений требует проверки. |
| 1С:УТ: справочники поставщиков и номенклатуры, ЕИ | Ночью | Сохранять историю там, где она есть; валидировать ключи и связи. Источник фактических изменений/удалений и частота обновления не описаны в ТЗ. |
| Курсы валют | Ночью после появления актуального набора | Проверить дату курса и полноту валют; не пересчитывать витрины на неполном наборе. |
| SRM contracts | Ночью, инкремент по `updatedFrom` | `size <= 100`; учитывать `X-Total-Count`; общий лимит API — 100 запросов/мин на OAuth2-токен. |
| SRM tenders | Первичная полная загрузка с checkpoint; повторный полный обход по расписанию не выполняется | `updatedFrom` отсутствует, сортировка relevance нестабильна. Страницы читаются по `page`, `size=100`; пустой ответ считается концом страниц — это допущение. После сбоя продолжаем с сохранённой страницы, но возможны пропуски из-за нестабильной сортировки. |
| SRM lots | Очередь по одному тендеру | Только один tender на запрос. Успех/ошибка фиксируются отдельно по тендеру. Неуспешные задания повторяются ограниченно, затем остаются в списке ошибок для отдельного повторного запуска. |
| WMS → Kafka `wms.receipts.v1` | Непрерывное потребление | Принимать as-is без требования немедленного изменения WMS. Сохранять исходное событие, валидировать поля, дедуплицировать по `event_id` при подтверждённой стабильности ID. |

### Слои и пересчёт

1. **Ingestion/raw:** исходные payload/файлы, метаданные загрузки, время получения, источник, статус обработки и ошибки. Сохранять исходное событие WMS для повторного разбора.
2. **Контроль качества:** обязательные поля, типы, допустимые статусы, дубликаты, ссылки на заказ/строку/поставщика, валидность дат и количества. Некорректные записи не терять: карантин + причина.
3. **Core:** нормализованные заказы и строки, приёмки, поставщики с историей, номенклатура, единицы измерения и курсы валют. Все преобразования должны быть воспроизводимыми и идемпотентными.
4. **Mart:** оборот закупок, цены за базовую единицу, OTIF, концентрация поставщиков и другие согласованные KPI.
5. **Публикация:** витрины пересчитываются после успешного завершения зависимых загрузок и DQ-проверок. Если обязательный источник не обновился, не выдавать витрину за полностью актуальную.

### Расписание и оркестрация

- Предложение для первого релиза: ночной пакетный запуск в конфигурируемое время; целевой ориентир готовности — к 08:00 МСК в рабочие дни, если заказчик подтвердит SLA.
- Kafka-потребитель работает непрерывно; накопившиеся события учитываются в очередном расчёте витрин.
- Оркестратор запускает этапы по зависимостям: источники → raw → DQ → core → marts → публикация статуса.
- Ограничение параллелизма и общий rate limiter применяются ко всем SRM-вызовам на токене; независимые задания могут выполняться параллельно в пределах лимитов.
- Время 08:00 МСК — предлагаемая цель, не исходное требование ТЗ.

### Свежесть и аварии

На дашборде/странице статуса показывать `last_success_at` по каждому источнику и витрине, статус `OK` / `PARTIAL` / `STALE`, число ошибок и необработанных сущностей. Если ночная загрузка не завершилась, зависимые витрины не маркировать как актуальные; уведомить ответственных по согласованному каналу. SLA уведомления и порог `STALE` — настраиваемые параметры, которые требуется утвердить.

Checkpoint сохраняется только после долговременного сохранения соответствующей единицы работы. После перезапуска возобновлять с checkpoint. Для tenders сохранение номера страницы позволяет продолжить, но не обеспечивает полноту при меняющейся сортировке. Полный повторный обход тендеров не выполняется согласно решению заказчика.

## 4.2. SRM API: требования к интеграции

### Подтверждено исходным фрагментом ТЗ

- `GET /api/v2/contracts?page={n}&size={100}&updatedFrom={ISO8601}`; `size` не более 100; ответ содержит `X-Total-Count`.
- `GET /api/v2/tenders?page={n}&size={100}`; параметра `updatedFrom` нет; около 180 000 записей; сортировка по relevance и порядок между вызовами не гарантирован.
- `GET /api/v2/tenders/{id}/lots`; только один тендер на запрос, batch endpoint не описан.
- OAuth2 `client_credentials`, TTL токена 15 минут.
- Лимит 100 запросов/мин на токен указан у contracts; для проектирования считаем его общим для contracts/tenders/lots — допущение, требующее подтверждения владельца API.

### Инкрементальность

**Contracts:** запрашивать изменения от checkpoint `updatedFrom`; `size <= 100`; сохранять результаты идемпотентно по стабильному ID; обновлять checkpoint после успешного сохранения страницы/набора. Предусмотреть overlap и дедупликацию, но длительность overlap и семантику границы `updatedFrom` подтвердить отдельно.

**Tenders:** инкремент по API сделать надёжно невозможно на основании доступного описания: нет `updatedFrom`, стабильный порядок не гарантирован. Принятое решение — первичный полный обход, `size=100`, следующая страница до пустого ответа (допущение), сохранение прогресса и продолжение после сбоя с последней сохранённой страницы. Повторный полный обход по расписанию не делать. Это оставляет риск пропуска новых/перемещённых записей; не заявлять гарантию полноты. Для устранения риска в будущем запросить у SRM фильтр по дате/изменению или стабильную сортировку/snapshot token.

**Lots:** создавать отдельное задание на каждый tender ID; сохранять результат и статус отдельно; ошибка одного тендера не останавливает очередь. Неуспешные задания после ограниченных повторов маркировать `FAILED` и разрешать повторно запустить только их.

### Лимит запросов и оценка объёма

Размер страницы tenders — 100, объём — около 180 000 записей. Оценка запросов для полного обхода: `180000 / 100 = 1800` запросов страниц при условии ровно 100 записей на каждой полной странице. Поштучная загрузка лотов: приблизительно `180000` запросов, если лоты запрашиваются для каждого тендера. Итого без contracts, токенов, повторов и ошибок: `1800 + 180000 = 181800` запросов. При лимите 100 запросов/мин теоретическая нижняя граница: `181800 / 100 = 1818` минут, то есть около 30,3 часа. Это оценка, а не SLA: она предполагает общий лимит 100 req/min, 100 записей на полной странице и один lots-вызов на тендер. В расчёт не включены ошибки, задержки, другие endpoint и повторные попытки.

Обязателен централизованный token-aware rate limiter, который не позволяет превышать 100 запросов/мин. Для production заложить запас ниже лимита, например конфигурируемую цель 80–90 запросов/мин; точное значение подобрать по наблюдениям. Не запускать параллельные независимые лимитеры для разных endpoint.

### OAuth2

- Получать токен через `client_credentials`.
- Использовать срок жизни из ответа OAuth2 (`expires_in`); TTL 15 минут указан в ТЗ, поле `expires_in` — ожидаемый стандартный механизм, но конкретный ответ надо проверить.
- Обновлять токен заранее, с буфером времени; не ждать 401.
- По согласованному проектному требованию при истечении/недействительности токена API возвращает `401` с описанием ошибки. Это не подтверждено исходным фрагментом ТЗ.
- При 401 один раз получить новый токен и ограниченно повторить исходный запрос; не допускать бесконечного цикла. Если повтор неудачен — записать ошибку и сохранить прогресс.

### Отказоустойчивость для всех запросов

- Таймаут соединения: стартовая настройка 5 секунд; таймаут ответа: 30 секунд. Значения конфигурируемые и подлежат настройке по фактическим SLA API.
- До 3 повторов сверх первоначальной попытки для временных ошибок (сетевые сбои, timeout, HTTP 5xx, 429); конфигурируемый экспоненциальный backoff с jitter.
- Для HTTP 429 учитывать общий лимит; если есть `Retry-After`, соблюдать его. Наличие заголовка не подтверждено.
- Для обычных 4xx не повторять автоматически; исключения — отдельно обработанные 401 и 429.
- Сохранять checkpoint только после durable save; upsert по стабильным ID; сохранять параметры задания, номер попытки, endpoint, длительность, код ответа и текст ошибки. Не логировать секреты/токены.
- Ограничивать параллелизм, отслеживать число запросов/мин, 401/429/5xx, таймауты, длительность и глубину очереди.

### Сбой на 130-й тысяче

При аварии после примерно 130 000 из 180 000 тендеров: сохранить последнюю успешно сохранённую страницу и отдельные статусы lots-заданий; после восстановления продолжить с сохранённого checkpoint, не перезапуская весь процесс. Успешные записи upsert-ятся идемпотентно; ошибки конкретных тендеров обрабатываются отдельно. Для нестабильной сортировки продолжение с page checkpoint не гарантирует полноту, это открытый риск API, а не проблема, которую можно полностью решить локальным checkpoint.

## 4.3. Контракт события приёмки Kafka

### As-is от WMS

```json
{
  "event_id": "b1f2...",
  "ts": "2026-08-11T09:14:22Z",
  "warehouse": "WH-03",
  "order": "PO512345",
  "line": 2,
  "qty": 40.0,
  "status": "accepted"
}
```

Это пример из ТЗ, не полная спецификация. Типы, обязательность, семантика статусов, уникальность `event_id` и гарантии порядка со стороны WMS требуют подтверждения.

### Целевой контракт, который запросить у WMS

Предлагаемый JSON Schema (draft 2020-12; схема проекта, не текущий формат WMS):

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://schemas.example.invalid/wms/receipt-event-v1.schema.json",
  "title": "ReceiptEvent",
  "type": "object",
  "additionalProperties": false,
  "required": ["schema_version", "event_id", "occurred_at", "warehouse_id", "order_id", "line_no", "quantity", "status"],
  "properties": {
    "schema_version": {"type": "integer", "const": 1},
    "event_id": {"type": "string", "minLength": 1},
    "operation_id": {"type": ["string", "null"]},
    "occurred_at": {"type": "string", "format": "date-time"},
    "sequence_number": {"type": ["integer", "null"], "minimum": 0},
    "warehouse_id": {"type": "string", "minLength": 1},
    "order_id": {"type": "string", "minLength": 1},
    "line_no": {"type": "integer", "minimum": 1},
    "quantity": {"type": "number", "minimum": 0},
    "status": {"type": "string", "minLength": 1}
  }
}
```

`example.invalid` — placeholder namespace, заменить на реестр схем клиента. `operation_id` и `sequence_number` целевые пожелания к WMS. Нельзя считать их присутствующими в as-is. `quantity >= 0` — предварительное правило; возвраты/корректировки могут требовать отрицательных значений или отдельного типа события и должны быть согласованы.

**Ключ Kafka:** целевой ключ — `warehouse_id|order_id|line_no` для порядка событий одной строки в рамках партиции. Если требуется порядок по конкретной операции приёмки, уточнить бизнес-ключ. Kafka сохраняет порядок в одной партиции, но не восстанавливает порядок, потерянный до публикации; для достоверного порядка нужен `sequence_number` от WMS.

**Доставка и идемпотентность:** at-least-once. Потребитель дедуплицирует по `event_id` в устойчивом хранилище; запись дедупликационного ключа и применение события выполняются атомарно в локальной БД. Уникальность и неизменность `event_id` — предположение до подтверждения WMS. Outbox используется для публикации наших производных событий в Kafka, если они появляются; входящий WMS topic сам по себе не требует Outbox на стороне WMS.

**Out-of-order:** если есть `sequence_number`, применяем события по последовательности, а при пропуске ставим сущность на reconciliation/ожидание и поднимаем метрику. Если последовательности нет, используем `ts` только как эвристику; равные timestamps разрешаем детерминированно по `event_id`, но не утверждаем, что это реальный бизнес-порядок. События, которые могут изменить итоговый статус, требуют правил переходов статусов от WMS.

**Дубли:** `event_id` уже обработан — повтор не меняет состояние второй раз; повтор учитывается в метриках. Если один `event_id` пришёл с отличающимся payload, помещаем в карантин/DLQ как конфликт, не перезаписываем молча.

**Версионирование:** `schema_version` в payload и версионированный topic/registry; обратно совместимые необязательные поля можно добавлять по согласованной политике. Удаление/переименование обязательного поля или смена типа — breaking change, новая major-версия топика/схемы и период миграции потребителей.

### Что делаем сейчас, пока WMS не изменила формат

- Читаем `wms.receipts.v1` as-is; не требуем новых полей на стороне производителя.
- Сохраняем исходный payload и метаданные Kafka (topic/partition/offset/время получения).
- Валидируем наличие полей примера и корректность типов; невалидные сообщения сохраняем в карантин/DLQ с причиной, не теряя raw.
- Дедуплицируем по `event_id`, только если проверка данных подтверждает его стабильность/уникальность; конфликты одинакового ID с разным содержимым отправляем на разбор.
- `ts` трактуем как timestamp события, но не как гарантированный sequence. Не делаем необоснованных выводов о порядке.
- Создаём адаптер `as-is → canonical`, чтобы целевой контракт не требовал одновременного изменения всех downstream-компонентов.

### Outbox, доставка исходящих событий и компенсация

Для исходящих событий, которые формирует наша интеграция, используем transactional outbox: изменение локальных данных и запись события фиксируются одной DB-транзакцией. Publisher отправляет событие в Kafka и помечает его опубликованным после broker ack. Гарантия — at-least-once; дубли возможны при потере подтверждения, потребители должны дедуплицировать по `event_id`.

После исчерпания конфигурируемых повторов сообщение публикуется в отдельный Kafka DLQ topic; ошибка и статус остаются в Outbox. Сначала требуется подтверждение записи в DLQ, затем исходная операция помечается как направленная в DLQ. Нужна процедура reconciliation на случай сбоя между publish и обновлением статуса. Название DLQ topic и параметры retention — конфигурация, конкретное имя пока не задано.

Компенсация внешнего действия — отдельная операция с собственным ID и статусом, например `COMPENSATION_PENDING`, `COMPENSATION_DONE`, `COMPENSATION_FAILED`; она не удаляет первоначальное событие. Если компенсация не удалась после повторов, направляем соответствующее событие/задание в DLQ и оставляем исходную операцию с явным статусом «компенсация не выполнена». Нельзя обещать откат в системе-получателе, если её контракт не поддерживает компенсирующую команду.

## 4.5. Допущения и открытые риски

1. Общий лимит 100 req/min для всех SRM endpoint — допущение; в фрагменте явно указан у contracts.
2. Пустая страница tenders означает конец данных — допущение.
3. Полный обход tenders не повторяется по расписанию; это согласованное решение, но оно означает отсутствие надёжного обнаружения новых/изменённых тендеров.
4. Продолжение tenders с сохранённого номера страницы после сбоя не гарантирует полноту из-за нестабильной сортировки.
5. HTTP 401 с описанием ошибки и `expires_in` — целевое требование/предположение, не подтверждённое фрагментом ТЗ.
6. Таймауты 5/30 секунд и до 3 повторов — начальные конфигурационные значения, а не контракт API.
7. WMS рассматривается как чёрный ящик. `operation_id`, `sequence_number`, семантика статусов и стабильность `event_id` — требования к целевому контракту/допущения, а не подтверждённые свойства текущей системы.
8. Целевая готовность витрин к 08:00 МСК — предложение, требующее подтверждения заказчика.
9. Не определены конкретный оркестратор, канал оповещения, SLA свежести, названия Kafka DLQ topics и retention — выбрать в рамках технического проектирования.

## 4.6. Бизнес-процессы: участники, последовательность, артефакты и результат

Ниже бизнес-процессы описаны отдельно от sequence diagrams. Диаграммы показывают обмен сообщениями и технические ветвления; таблицы фиксируют ответственность, входы/выходы и контрольные результаты. Внешние вызовы не считаются частью единой распределённой транзакции: атомарность гарантируется только внутри локальной транзакции БД.

### BP-01. Ночная загрузка данных из 1С:УТ

**Участники:** планировщик/оркестратор; адаптер чтения PostgreSQL-реплики 1С:УТ; хранилище raw; DQ-процесс; core-модель; журнал запусков/мониторинг.

| Шаг | Действие | Артефакт на этапе | Результат / контроль |
|---|---|---|---|
| 1 | Оркестратор запускает загрузку по расписанию | `run_id`, конфигурация запуска, стартовый timestamp | Создан запуск с корреляционным ID |
| 2 | Адаптер читает заказы, строки и справочники из доступной реплики | Выборка источника, параметры инкремента, checkpoint | Получены записи за выбранный диапазон; инкремент по `updated_at` применяется только после проверки его семантики |
| 3 | Записи сохраняются в raw с метаданными источника | Raw-записи, `run_id`, время извлечения, ключ источника | Исходные данные доступны для повторной обработки и аудита |
| 4 | DQ проверяет типы, обязательные поля, ключи, даты и ссылки | DQ-отчёт, карантин записей с причинами | Валидные записи идут дальше; невалидные не теряются молча |
| 5 | Валидные записи преобразуются в core идемпотентным upsert | Журнал преобразования, количество обработанных/отклонённых записей | Core обновлён без повторного создания дублей |
| 6 | Фиксируется checkpoint и статус этапа | Новый checkpoint, статистика этапа | Checkpoint продвигается только после durable save; при сбое запуск можно возобновить |

**Результат BP-01:** обновлённый raw и core по данным 1С:УТ, DQ-отчёт, checkpoint и статус загрузки. **Открытые условия:** доступность реплики, гарантия полноты `updated_at`, семантика удаления/отмены и расписание обновления справочников должны быть подтверждены технически.

### BP-02. Ночная загрузка SRM contracts

**Участники:** оркестратор; SRM OAuth2; API-клиент; общий rate limiter; SRM API; raw/core; checkpoint и мониторинг.

| Шаг | Действие | Артефакт на этапе | Результат / контроль |
|---|---|---|---|
| 1 | Оркестратор создаёт задание contracts с сохранённым `updatedFrom` | `run_id`, checkpoint, параметры `page/size/updatedFrom` | Задание можно повторить с теми же параметрами |
| 2 | API-клиент получает действующий токен либо обновляет его по `expires_in` | Токен в защищённой памяти, время истечения | Секрет не попадает в логи; обновление выполняется заранее |
| 3 | Каждый запрос проходит через общий rate limiter | Запись о времени запроса/endpoint | Ограничение не превышается совместно с tenders и lots |
| 4 | Клиент запрашивает страницу contracts | HTTP-ответ, `X-Total-Count`, параметры страницы | Ответ проверен; 401/429/5xx и timeout обрабатываются отдельными ветками |
| 5 | Данные сохраняются идемпотентно в raw/core | Raw payload, результат upsert, DQ-отчёт | Повтор ответа не создаёт дубли |
| 6 | После сохранения обновляется checkpoint | `updatedFrom` и статус завершённого участка | Неуспешный участок не отмечается завершённым |

**Результат BP-02:** обновлённые договоры и сохранённый checkpoint. **Ограничение:** overlap для границы `updatedFrom` и правила включительности timestamp требуют настройки после проверки API.

### BP-03. Первичный обход SRM tenders и загрузка lots

**Участники:** оркестратор; очередь тендеров/lots; OAuth2; API-клиент; общий rate limiter; SRM API; raw/core; хранилище состояния и мониторинг.

| Шаг | Действие | Артефакт на этапе | Результат / контроль |
|---|---|---|---|
| 1 | Создаётся задание первичной выгрузки tenders | `run_id`, начальная страница, конфигурация `size=100` | Запуск имеет устойчивый ID |
| 2 | Клиент получает страницу и сохраняет данные идемпотентно | Raw-ответ, записи tenders, статистика страницы | Страница считается обработанной только после сохранения |
| 3 | Сохраняется checkpoint последней успешно сохранённой страницы | Номер страницы, статус, timestamp | При падении можно продолжить с сохранённой позиции |
| 4 | Если ответ пустой, обход завершается | Признак окончания обхода | Пустой ответ — принятое допущение, не описанное в исходном API-фрагменте |
| 5 | Для каждого сохранённого tender ID создаётся отдельное lots-задание | Очередь `tender_id`, статус `PENDING` | Поштучный endpoint не блокирует обработку остальных тендеров |
| 6 | Lots-задание выполняет запрос с общим rate limiter и ограниченными повторами | Payload лотов или журнал ошибки | Успешные данные сохраняются; ошибка отдельного тендера изолирована |
| 7 | После исчерпания повторов lots-задание помечается `FAILED` и доступно для выборочного перезапуска | `tender_id`, attempts, последняя ошибка | Перезапуск не требует повторного обхода всех тендеров |
| 8 | При восстановлении после падения продолжается с checkpoint; полный повторный обход не запускается | Состояние задания и checkpoint | Риск пропусков из-за нестабильной сортировки остаётся и явно отображается |

**Результат BP-03:** доступные тендеры и лоты, checkpoint, перечень ошибок по отдельным тендерам. **Критичный риск:** API без `updatedFrom` и стабильной сортировки не даёт гарантии полноты при продолжении с номера страницы; по согласованному решению повторный полный обход не выполняется.

### BP-04. Непрерывное потребление WMS receipt events

**Участники:** WMS (внешний чёрный ящик); Kafka topic `wms.receipts.v1`; consumer; raw-хранилище; валидатор/адаптер as-is → canonical; dedup store; core; карантин/DLQ; мониторинг.

| Шаг | Действие | Артефакт на этапе | Результат / контроль |
|---|---|---|---|
| 1 | Consumer читает сообщение из Kafka | Topic, partition, offset, payload, время получения | Положение consumer можно контролировать и восстанавливать |
| 2 | Исходное сообщение сохраняется в raw | Неизменённый payload и Kafka metadata | Есть возможность повторной обработки после изменения правил |
| 3 | Валидатор проверяет поля as-is и преобразует в canonical | Результат валидации, версия адаптера | Невалидные сообщения направляются в карантин/DLQ с причиной |
| 4 | Проверяется `event_id` и наличие уже применённого события | Dedup key, результат проверки | Дубль не применяет бизнес-изменение повторно; уникальность ID пока предположение |
| 5 | Событие применяется к core в локальной транзакции вместе с записью о применении | Изменение core + запись обработанного `event_id` | Повторное получение безопасно при устойчивом dedup store |
| 6 | Offset подтверждается после durable save | Committed offset | Сбой до commit приводит к повторной доставке, но не к повторному бизнес-эффекту при корректной идемпотентности |
| 7 | Контролируются задержка, ошибки и порядок | Lag, DQ-метрики, карантин | При отсутствии sequence поле `ts` используется только как эвристика, не как гарантия порядка |

**Результат BP-04:** факты приёмки в raw/core, контроль offset, дедупликация и метрики свежести. **Важно:** конкретная семантика Kafka consumer group, гарантия стабильности `event_id` и допустимый порядок требуют проверки в текущем контуре; WMS пока не предполагается изменять.

### BP-05. Публикация исходящего события через Transactional Outbox

**Участники:** сервис интеграции; локальная БД; таблица Outbox; Publisher; основной Kafka topic; потребитель; мониторинг.

| Шаг | Действие | Артефакт на этапе | Результат / контроль |
|---|---|---|---|
| 1 | Сервис изменяет локальные данные и создаёт Outbox-запись в одной транзакции БД | Бизнес-изменение + `event_id` + payload + статус `PENDING` | Нет состояния, в котором изменение закоммичено, а Outbox-запись отсутствует |
| 2 | Publisher выбирает ожидающее событие | Claim/lease, номер попытки | Конкурирующие Publisher не обрабатывают одну запись одновременно без механизма блокировки/lease |
| 3 | Publisher отправляет событие в Kafka | Payload, key, correlation ID | Ключ и схема соответствуют контракту события |
| 4 | После broker ack фиксируется `PUBLISHED` | Ack и timestamp публикации | Сбой после ack, но до обновления статуса может привести к дублю; это ожидаемо для at-least-once |
| 5 | При временной ошибке событие остаётся доступным для повтора | attempt count, last error, next retry at | Backoff ограничивает повторную нагрузку |
| 6 | После исчерпания попыток Publisher отправляет сообщение в DLQ topic | Исходное событие + error metadata | Перенос считается успешным только после ack DLQ |
| 7 | Статус Outbox обновляется после подтверждённой публикации в DLQ | `DLQ`, причина, время | Reconciliation выявляет случаи публикации в DLQ без обновлённого статуса или наоборот |

**Результат BP-05:** надёжная публикация с гарантией at-least-once, аудит попыток и контролируемая DLQ. Outbox даёт атомарность только между локальным изменением и записью Outbox, не между БД и Kafka.

### BP-06. Компенсация внешнего действия

**Участники:** оператор/политика компенсации; сервис интеграции; БД и журнал изменений; Outbox Publisher; внешний сервис/потребитель; Kafka и DLQ; мониторинг.

| Шаг | Действие | Артефакт на этапе | Результат / контроль |
|---|---|---|---|
| 1 | Принимается решение о компенсации по конкретной исходной операции | Ссылка на исходный `operation_id`, причина и инициатор | Компенсация трассируется к первоначальному действию |
| 2 | Проверяется, поддерживает ли внешний получатель компенсирующую команду | Контракт получателя, текущее состояние/версия | Без поддержки получателя нельзя обещать внешний откат |
| 3 | Создаётся отдельная компенсационная операция и Outbox-запись | `compensation_id`, исходный `operation_id`, payload, статус `COMPENSATION_PENDING` | Исходная запись сохраняется; история не удаляется |
| 4 | Publisher отправляет компенсирующую команду/событие | Сообщение с correlation ID и idempotency key | Повтор не должен выполнять компенсацию дважды |
| 5 | Результат подтверждается по контракту внешнего получателя | Ack/результат выполнения | Только подтверждённый результат переводит операцию в `COMPENSATION_DONE` |
| 6 | После исчерпания повторов фиксируется `COMPENSATION_FAILED`, сообщение уходит в DLQ | Ошибка, attempts, DLQ record | Статус исходной операции не утверждает, что откат завершён |

**Результат BP-06:** аудируемая попытка компенсации. Сам факт публикации команды в Kafka не означает, что внешняя система успешно откатила действие; нужен контракт подтверждения результата или reconciliation.

### BP-07. Ночная оркестрация, публикация витрин и информирование заказчика

**Участники:** оркестратор; коннекторы источников; raw/DQ; core; mart jobs; сервис статуса/уведомлений; заказчик/дежурный.

| Шаг | Действие | Артефакт на этапе | Результат / контроль |
|---|---|---|---|
| 1 | По конфигурируемому расписанию запускается run | `run_id`, план зависимостей, ожидаемое время готовности | Запуск отслеживается сквозным correlation ID |
| 2 | Выполняются загрузки источников; WMS consumer продолжает работать независимо | Статусы этапов, checkpoints, raw | Независимые процессы не блокируют поступление WMS-событий |
| 3 | Выполняются DQ и сверки обязательных наборов | DQ summary, число ошибок и карантина | Критические нарушения не маскируются успешным статусом |
| 4 | Core обновляется после успешной загрузки соответствующих источников | Версия/время обновления core | Core отражает доступные проверенные данные |
| 5 | Оркестратор определяет готовность каждой витрины по её зависимостям | Матрица зависимостей, DQ gates | Витрины рассчитываются только на достаточном наборе данных |
| 6 | При полном успехе публикуется `OK`; при неполных необязательных данных — `PARTIAL`; при отсутствии критичного источника — `STALE` для зависимых витрин | `last_success_at`, `status`, причины и ошибки | Подтверждённая политика статусов; не выдавать устаревшую витрину за актуальную |
| 7 | Сервис статуса показывает актуальность и уведомляет ответственных | Страница/метрика статуса, уведомление | Заказчик видит время последнего успешного обновления и причину отклонения |
| 8 | После исправления причины оркестратор возобновляет нужные этапы с checkpoint | Retry run, checkpoint, история попыток | Не требуется безусловно запускать весь pipeline с начала |

**Результат BP-07:** витрины с явным статусом актуальности, журнал выполнения и уведомления. Целевой ориентир готовности к 08:00 МСК — предложение, требующее согласования; SLA и канал уведомлений остаются конфигурируемыми до решения заказчика.

### Политика статусов витрин (согласовано)

- `OK` — все обязательные источники и проверки, необходимые конкретной витрине, завершились успешно.
- `PARTIAL` — витрина рассчитана, но отсутствуют или отложены необязательные данные; отображаются причины и охват неполноты.
- `STALE` — не обновился критичный для витрины источник либо не завершились обязательные этапы; старые данные не выдаются за актуальные.
- Статус и `last_success_at` ведутся по каждой витрине отдельно: сбой не связанного с ней источника не должен автоматически делать все витрины `STALE`.
