## ! Подтверждение выполнения в PostgreSQL
Скриншоты запусков Q1, Q2 и Q3 в PostgreSQL приложены отдельно и предназначены для подтверждения требования задания: к SQL нужно приложить результат реального запуска (CSV или скриншот). Перед отправкой убедитесь, что все три изображения находятся в этом каталоге, открываются и на них видны результат и отсутствие ошибки.

CSV и скриншоты — разные артефакты. Не утверждайте, что CSV экспортирован из PostgreSQL, если он получен другим движком. Скриншот подтверждает только видимый на нём запуск и не заменяет проверку полноты результата.

## Зафиксированные допущения
- Дата отсечения пилота из легенды — 2026-08-12; шесть полных месяцев для Q1 интерпретированы как 2026-02-01—2026-07-31.
- Для демонстрации выбрана последняя версия строки по `updated_at DESC, source_row_no DESC`; семантика `updated_at` не подтверждена, поэтому это допущение, не официальный бизнес-правил.
- OTIF считается по строке: полное количество принято в срок, а в принятом количестве учитываются только события со статусом `accepted`. Требует согласования статусов отмены, частичного брака, временной зоны и правил единиц измерения.
- Q2 использует последний полный квартал относительно даты легенды: 2026-04-01—2026-06-30. Курс соединяется по дате заказа, что является временным техническим выбором, а не подтверждённым правилом финансового учёта.
- Q2: медиана по другим поставщикам рассчитана по их средневзвешенной цене за базовую ЕИ; только позиции с доступной ценой минимум у одного другого поставщика попадают в сравнение.
- Q3 сумма закупки считается как `qty * price * FX`, по дате заказа, без отдельного подтверждения НДС/скидок/финансового признания. Это аналитическая оценка, не бухгалтерский оборот.
- В контрольных CSV возможны экстремальные отклонения из-за ошибок исходных цен, разных упаковок или неизвестной семантики цены; результаты предназначены для анализа аномалий, а не как готовый рейтинг поставщиков.

## Производительность при росте в 100×
Основной риск — оконные функции и медиана по каждому item × supplier на широкой таблице версий, а также повторное соединение с курсами и справочниками. Для PostgreSQL: сначала разрешать версии в инкрементальной staging-таблице после согласования правила; партиционировать факты по дате события/заказа; индексировать `(order_id, line_no)`, `(supplier_id, valid_from, valid_to)`, `(item_id, order_date)` и `(rate_date, currency)`; материализовать daily/quarterly aggregates; медиану считать на агрегированной таблице item-supplier-period; анализировать `EXPLAIN (ANALYZE, BUFFERS)` и настраивать incremental refresh. Не создавать индексы вслепую — подтвердить планы и селективность на объёме.
